# 事故與故障處理指引

老虎機的故障處理有一項與一般軟體不同的特性：**故障可能已經影響玩家的金錢權益**。因此處理程序不只是修復，還包含玩家補償、監管機關通報與證據保全。

---

## 1. 核心原則

### 1.1 「故障使遊戲與派彩無效」

博彩業的傳統條款是 *Malfunction voids all pays and plays*（故障使所有派彩與遊戲無效）。但**不能把它當作萬用免責條款**：

- 多數監管機關要求該條款須在遊戲規則中**明確揭露**才可主張
- 監管機關普遍不接受營運商以此條款規避「玩家因故障而受損」的補償責任
- 若故障導致玩家獲得不當利益，追回的可行性通常低於預期，且追回行為本身可能引發爭議

**顧問立場**：這個條款應視為**最後手段**，而非事故處理的預設方案。正確的設計目標是讓故障不會影響已決定的結果（見 `platform-systems-compliance.md` §3）。

### 1.2 對玩家有利的推定

發生無法完全重建的事故時，實務上對玩家有利的處理（維持玩家獲利、退還投注）在監管上的風險遠低於相反做法。監管機關評估的是營運商是否公平對待玩家，而非是否精算正確。

這不代表要接受詐欺，而是說：**在事實不明確時，成本應由營運方吸收。**

---

## 2. 事故分類

| 等級 | 定義 | 範例 | 通報 |
|------|------|------|:---:|
| **P1 致命** | 影響遊戲公平性或結果正確性 | RNG 異常、賠付計算錯誤、RTP 偏離宣稱值、未認證建置上線 | ✅ 立即 |
| **P2 重大** | 影響玩家資金或合規功能 | 錢包餘額錯誤、重複扣款、自我排除失效、限額未生效、已排除玩家能遊玩 | ✅ 立即 |
| **P3 中度** | 影響服務可用性但不影響結果正確性 | 遊戲無法載入、斷線率異常、game recall 不可用 | ⚠️ 視市場 |
| **P4 輕微** | 呈現層問題 | 動畫錯誤、文字錯誤（不含規則與揭露） | ❌ 記錄 |

### 2.1 必然屬於 P1／P2 的情況

以下無論影響範圍多小，都應以最高等級處理：

- 使用非 CSPRNG 決定結果（即使只影響一款遊戲）
- 客戶端能影響結果
- 已自我排除玩家能夠下注（含中央系統整合失效導致 fail-open）
- 低於法定年齡玩家能夠下注
- 實際 RTP 與宣稱值有系統性偏離
- 生產環境運行未經認證的建置
- 稽核日誌遺失或可被篡改
- 投注上限未生效（英國 £5/£2、德國分級）

這些不只是缺陷，而是**牌照條件違反**，可能觸發監管調查。

## 3. 事故處理流程

### 3.1 標準程序

```
偵測
  ↓
1. 止血：停止受影響遊戲／功能（不是先修，是先停）
  ↓
2. 證據保全：凍結日誌、快照建置雜湊值與設定檔、保存 RNG 序列
  ↓
3. 影響範圍界定：受影響玩家清單、局數、金額
  ↓
4. 分類（依 §2）與通報決定
  ↓
5. 監管機關通報（P1/P2 立即；依市場時限）
  ↓
6. 根因分析
  ↓
7. 玩家補償執行
  ↓
8. 修復與重新認證判定（見 change-management-recert.md）
  ↓
9. 事後報告與預防措施
```

### 3.2 為何「先停後修」

工程直覺是快速修復並部署。在博彩系統中這是錯的，原因有二：

1. **緊急修復繞過認證流程**，導致生產環境運行未認證建置——把一個事故變成兩個
2. **修復可能破壞證據**，使影響範圍無法界定，進而無法正確補償玩家或回答監管機關的詢問

正確順序是停止服務、保全證據、界定範圍，然後才走正常的變更管理流程修復。

### 3.3 證據保全清單

事故發生時應立即保全：

- [ ] 受影響期間的完整稽核日誌（含 RNG 原始值）
- [ ] 生產建置的雜湊值與二進位檔
- [ ] 生效中的設定檔（賠率表、捲軸帶、市場設定檔）
- [ ] 系統設定與能力旗標狀態
- [ ] 錢包交易記錄
- [ ] 受影響玩家的帳戶狀態快照
- [ ] 中央系統整合的請求／回應記錄
- [ ] 監控與告警記錄
- [ ] 部署記錄（誰在何時部署了什麼）

**證據保全應為自動化程序**，因為事故當下的人力會集中在止血。

## 4. 玩家補償

### 4.1 判定原則

| 情況 | 建議處理 |
|------|---------|
| 玩家因故障少拿賠付 | 補足差額，並主動通知 |
| 玩家因故障多拿賠付 | 通常不追回；追回前應評估監管與聲譽風險 |
| 未完成局，結果已決定 | 依已決定結果完成賠付（見 `platform-systems-compliance.md` §3.1） |
| 未完成局，結果未決定 | 退還投注 |
| 多階段功能進度遺失 | 依中斷點合理重建，無法重建時對玩家有利處理 |
| 已自我排除玩家的下注 | 退還投注；獲利處理依市場規則（部分市場明文規定沒收，如賓州、德拉瓦、康乃迪克） |
| 未達年齡玩家的下注 | 退還投注、沒收獲利、關閉帳戶（多數市場要求） |

⚠️ **自我排除與未達年齡的獲利處理各市場不同**：康乃迪克規定自我排除者不得領取獎金、追回損失或接受招待；德拉瓦規定名單內者領取的獎金可被沒收；賓州、紐澤西各有規定。不要套用單一規則，須依 `templates/market-profiles/<market>.json` 個案確認。

### 4.2 補償記錄

每筆補償須記錄：事故編號、玩家識別、受影響局數、原始結果、補償金額、計算依據、核准人、執行時間。這是監管機關檢視事故處理是否公平的主要證據。

## 5. 監管機關通報

### 5.1 通報義務的來源

通報要求通常在**牌照條件**中，而非公開法規。因此：

- B2C 營運商應直接查閱自身牌照條件
- B2B 供應商通常向營運商通報，由營運商向監管機關通報——但供應商應確認合約中的通報時限，因為營運商的時限會回推成供應商的時限
- 已確認的例子：安大略 AGCO Internet Gaming Notification Matrix（2026-03 v1.6）逐項規定通報方式（HIGH）

### 5.2 通報內容

使用 `templates/advisory/incident-report.json`。核心欄位：

- 事故編號、偵測時間、發生時間、通報時間
- 分類等級與判定依據
- 受影響範圍：玩家數、局數、金額、市場
- 是否影響遊戲公平性、玩家資金、合規功能（三者分別回答）
- 已採取的即時措施
- 根因（初報時可為「調查中」）
- 玩家補償方案與執行狀態
- 修復計畫與重新認證判定
- 預防措施

### 5.3 通報的心態

不要試圖淡化。監管機關對「主動、完整、及時通報」的容忍度遠高於「事後被發現曾經隱匿」。後者通常從技術問題升級為誠信問題，處置嚴重程度不同量級。

## 6. 預防性設計

事故處理的最佳投資是讓事故不影響玩家權益。設計層面：

| 措施 | 防範的事故類型 |
|------|--------------|
| 結果由伺服器決定並先寫入日誌，再回傳客戶端 | 斷線導致結果不一致 |
| 錢包交易幂等性 | 重複扣款／入帳 |
| 多階段功能狀態持久化 | 進度遺失 |
| 中央系統整合 fail-closed | 自我排除失效 |
| 部署前合規閘門 | 未認證建置上線 |
| 建置－認證對應表 | 無法確認生產狀態 |
| 即時 RTP 監控與告警 | RTP 系統性偏離 |
| 稽核日誌不可篡改＋獨立複製 | 證據遺失 |
| 自動化證據保全 | 事故當下無人力保全 |

### 6.1 即時 RTP 監控值得單獨說明

在生產環境持續統計實際 RTP，並與宣稱值的信賴區間比對，是偵測數學模型或實作缺陷最有效的方式。

實作要點：以滾動窗口統計，窗口大小依波動性決定（見 `math-verification.md` §2.1）；告警門檻應基於統計顯著性而非固定百分比，否則高波動遊戲會持續誤報。
