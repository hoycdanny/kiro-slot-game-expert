# 變更管理與重新認證指引

認證是對**特定建置**的認證，不是對產品的永久許可。任何變更都必須先判定是否觸發重新認證。本指引提供變更分類框架與各市場的通報要求。

---

## 1. 核心原則

### 1.1 認證綁定的是建置，不是產品

實驗室核發的認證報告對應一個具有特定雜湊值的建置。上線建置與認證建置不一致，即為未經認證的軟體在生產環境運行——這在多數市場是牌照條件違反，在德國更直接構成非法賭博（§22a(1)：未獲許可的老虎機屬非法賭博）。

因此**每一次部署都必須能回答**：這個建置的雜湊值是否對應一份有效的認證報告？若否，是否落在允許的免通報變更範圍內？

### 1.2 三個問題決定變更路徑

面對任何變更，依序回答：

1. **是否影響遊戲結果、賠付或 RNG？** 是 → 幾乎必然需重新認證
2. **是否影響監管機關已審查的功能（RG 功能、限額、日誌、揭露）？** 是 → 需通報，可能需重新認證
3. **是否僅影響不涉及上述的呈現層？** 是 → 通常可免，但仍須記錄並確認市場規則

**預設立場應為「需要」而非「不需要」。** 錯誤地跳過重新認證的後果（下架、罰款、牌照風險）遠大於不必要的重新送測成本。

## 2. 變更分類框架

### 2.1 分類表

| 類別 | 變更內容 | 重新認證 | 通報 |
|------|---------|:---:|:---:|
| **A：數學模型變更** | 賠率表、捲軸帶、RTP 目標、波動性、獎勵功能機率、jackpot 貢獻率 | ✅ 必須 | ✅ |
| **B：RNG 變更** | RNG 演算法、熵源、種子管理、縮放／映射邏輯 | ✅ 必須 | ✅ |
| **C：遊戲規則變更** | wild 替代規則、scatter 判定、賠付線定義、multiplier 套用順序、評估順序 | ✅ 必須 | ✅ |
| **D：產品約束變更** | 循環時間、投注上限／級距、autoplay、turbo、多局 | ✅ 必須 | ✅ |
| **E：RG 功能變更** | 限額機制、自我排除整合、會話提醒、淨部位顯示、強制中斷 | ⚠️ 視市場 | ✅ |
| **F：系統架構變更** | RGS、錢包、PAM、獎池控制器、日誌子系統、部署位置 | ⚠️ 視市場 | ✅ |
| **G：揭露內容變更** | RTP 揭露文案、規則說明、最高獎金機率 | ⚠️ 視市場 | ✅ |
| **H：呈現層變更** | 美術資源、音效、動畫、本地化文字（不含規則與揭露） | ❌ 通常免 | ⚠️ 視市場 |
| **I：缺陷修復** | 依修復影響範圍歸入上述類別 | 依類別 | ✅ |
| **J：資安更新** | 依賴套件升級、修補程式 | ⚠️ 視影響 | ⚠️ |

### 2.2 容易被誤判為 H 類的變更

以下看似呈現層，實際會觸發重新認證：

| 變更 | 為何不是 H 類 |
|------|-------------|
| 加快捲軸動畫 | 可能使遊戲循環時間低於下限（英國 2.5s、德國 5s 平均） |
| 修改中獎音效觸發條件 | 若在回報 ≤ 投注額時播放，違反英國 RTS 14F 與安大略 2.20 |
| 新增「跳過動畫」按鈕 | 等同 slam stop，英國 RTS 14E 與安大略 2.19 禁止 |
| 本地化文字更新 | 若涉及規則說明或 RTP 揭露，屬 G 類 |
| 調整 demo 模式表現 | 瑞典 Spellag 14:5 要求免費試玩與真錢同機率 |
| 新增幣別顯示 | 德國 §22a(5) 禁止非歐元幣別／點數／單位換算 |
| 改變 UI 上 autoplay 的可見性 | 若伺服器仍接受連續請求，功能仍存在（見 `platform-systems-compliance.md` §2） |

**顧問提醒**：客戶最常在「只是改個動畫速度」這類變更上出事，因為團隊不認為那是合規變更，因此未經合規審查即上線。建議建立**部署前合規閘門**，由本表作為判定依據。

## 3. 各市場的變更與通報要求

| 市場 | 要求 | 信心 |
|------|------|------|
| **德國** | ⚠️ **最嚴格**：每一款老虎機需事前 GGL 個別許可，須提供可實際遊玩的版本；**重大變更需重新申請許可**；許可可隨時撤銷（§22a(1)） | HIGH |
| **安大略** | Standard 4.08 要求遊戲、RNG 與系統元件經 Registrar 核准或登記 ITL 認證，**明文包含後續修改**；另有 AGCO Internet Gaming Notification Matrix（2026-03 v1.6）規定各類事項的通報方式 | HIGH |
| **英國** | 遊戲與 RNG 結果須於上線前登錄 Games Register；年度遊戲測試稽核與年度獨立安全稽核 | HIGH |
| **丹麥** | 認證方案含 **SCP.06 變更管理**專章；2025 起牌照持有人與遊戲供應商各自直接提交認證 | HIGH |
| **GLI** | 另有 **Change Management Program Guide v1.0** 與 Composite Submission Requirements v2.0 | HIGH |
| 其他市場 | 通報門檻與程序未確認 | UNVERIFIED |

**安大略 Notification Matrix 值得特別取用**：它是公開文件，逐項列出哪些事項需要事前核准、哪些僅需通報、時限為何。即使不進安大略，它是設計內部變更管理流程的良好參考骨架。

**丹麥 SCP.06** 同樣是公開的變更管理標準，可作為內部流程的檢查清單。

## 4. 變更管理流程

### 4.1 建議流程

```
變更提案
   ↓
合規分類（依 §2.1 表格）
   ↓
├─ A/B/C/D 類 → 重新認證路徑
│     ↓
│  更新 PAR sheet／技術文件 → 內部驗證（見 math-verification.md §6）
│     ↓
│  實驗室送測 → 取得新認證報告 → 監管機關通報／申請
│     ↓
│  （德國：重新申請逐款許可）
│     ↓
│  部署，記錄新建置雜湊值與認證報告對應
│
├─ E/F/G 類 → 逐市場判定 → 通報 → 視結果決定是否送測 → 部署
│
└─ H 類 → 記錄 → 確認市場無通報要求 → 部署
```

### 4.2 必須維護的記錄

| 記錄 | 內容 |
|------|------|
| 建置－認證對應表 | 每個生產建置的雜湊值、對應認證報告編號、有效市場清單、生效日 |
| 變更登記簿 | 每次變更的分類、判定依據、審核人、送測狀態 |
| 認證有效期追蹤 | 各市場認證的到期日與續期需求 |
| 法規變動追蹤 | 目標市場法規更新，及其對既有認證的影響 |

**建置－認證對應表是稽核時最常被要求的文件。** 若無法即時回答「目前生產環境跑的是哪個認證建置」，稽核結果通常不利。

## 5. 法規變動導致的被動重新認證

除了主動變更，法規變動也會使既有認證失效或需要調整。近期實例：

| 市場 | 變動 | 對既有產品的影響 |
|------|------|-----------------|
| 英國 | 投注上限 £5／£2 於 2025-04-09 生效 | 所有超過上限的投注選項須移除 |
| 英國 | RTS 於 2025-10-31 更新、RTS 14 於 2026-01-12 修訂、另有 2026-06-30 生效變更 | 須逐條比對既有實作 |
| 英國 | 紅利投注要求上限 10 倍，2026-01-19 起 | 紅利機制須調整 |
| 德國 | 投注上限分級預定 2026-07-01 生效（MEDIUM） | 投注上限須改為動態解析（見 `jurisdiction-matrix.md` §1.2） |
| 瑞典 | Lag 2026:90 信用資金禁令，2026-04 全面生效 | 支付流程須調整 |
| 瑞典 | 2026-08-01 起 Spelpaus 須以 Actor ID／API key 查詢 | 整合須更新 |
| 內華達 | Regulation 14 於 2026-02-26 修訂生效，變更 ITL 須提供內容（14.400） | 送測包內容須調整 |
| 西維吉尼亞 | 179 CSR 10 於 2026-04-27 全新生效，2031-08-01 屆期 | 全套要求須重新比對 |
| 丹麥 | 修訂版認證方案 2025-07-01 起強制 | 須依新方案重新認證 |
| 葡萄牙 | 新集中自我排除入口 2026-04-08 上線 | 整合須更新 |

**因此法規變動追蹤是持續性義務，不是專案階段任務。** 顧問應建議客戶建立定期（建議每季）的法規變動審視機制，並將受影響市場的認證狀態納入風險登記冊（`templates/advisory/risk-register.json`）。

⚠️ 英國在 15 個月內有至少三次 RTS 變動。以「認證通過就完成」的心態管理英國市場產品，必然會出現不合規期間。

## 6. 常見錯誤

| 錯誤 | 後果 |
|------|------|
| 熱修復（hotfix）繞過合規審查直接上線 | 生產建置與認證建置不一致 |
| 認為「只改美術」不需審查 | 動畫速度、音效觸發、跳過按鈕都可能違規（見 §2.2） |
| 多市場共用建置但只在一個市場送測 | 其他市場運行未認證軟體 |
| 依賴套件自動升級 | 建置雜湊值改變，且可能引入未審查的行為變更 |
| 未追蹤法規變動 | 產品在法規生效日後即不合規（見 §5） |
| 未維護建置－認證對應表 | 稽核時無法證明合規 |
| 假設 GLI 認證涵蓋所有市場 | 各市場有獨立核准要求（德國逐款許可、安大略 Registrar 核准） |
