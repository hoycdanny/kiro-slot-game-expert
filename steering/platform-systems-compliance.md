# 平台與系統層合規指引

老虎機的合規範圍不止於遊戲邏輯。實驗室與監管機關審查的是**整個系統**：遠端遊戲伺服器、玩家帳戶錢包、獎池控制器、日誌基礎設施、以及與監管機關中央系統的整合。本指引涵蓋 GLI-19 系統層要求與各市場的平台級約束。

---

## 1. 系統邊界與責任劃分

### 1.1 GLI-19 涵蓋的系統元件

GLI-19（Interactive Gaming Systems v3.0，2020-07-17）的審查範圍包含：

| 元件 | 說明 |
|------|------|
| Remote Gaming Server (RGS) | 決定遊戲結果、執行規則評估的伺服器 |
| Player Account Management (PAM) | 玩家帳戶、身分、限額、自我排除狀態 |
| Wallet | 餘額、投注扣款、獎金入帳的交易系統 |
| Game Client | 玩家端呈現層 |
| Jackpot Controller | 累積獎金貢獻與命中處理（另見 GLI-12 v3.0） |
| Logging / Audit Subsystem | 稽核日誌與重要事件記錄 |
| RNG | 隨機數來源（見 `rng-game-logic.md`） |

**送測範圍常見誤解**：客戶常以為只需送測遊戲。實際上西維吉尼亞 179 CSR 10 §5.7.2.b 明確對**每一台互動遊戲系統伺服器，包含遠端遊戲伺服器與玩家帳戶錢包**設有要求；安大略 Standard 4.08 要求「接受、處理、決定結果、顯示與記錄玩家投注細節」的所有元件——含 RNG 與遠端遊戲伺服器——都須經 Registrar 核准或登記 ITL 認證，**且含後續修改**。

### 1.2 誰負責哪一段

責任邊界矩陣見 `advisory-engagement.md` §3。此處補充系統層的實務界面：

- **B2B 遊戲供應商**通常提供 RGS 與遊戲，由營運商提供 PAM 與錢包。此時**整合介面的合規責任容易落空**：例如自我排除狀態必須在投注前檢查，但若供應商假設營運商已檢查、營運商假設供應商會檢查，就會出現已自我排除玩家仍能下注的重大違規。
- 顧問應要求明確的**介面合規責任矩陣**，逐項確認每個檢查點由哪一方執行、以及失敗時的行為（fail-closed 而非 fail-open）。

## 2. 結果必須由伺服器決定

這是最基本也最常被違反的架構要求。

**要求**：遊戲結果必須完全由伺服器端決定，客戶端僅負責呈現。客戶端不得持有能推導結果的資訊，不得參與結果決定。

**常見違規模式**：

| 模式 | 為何違規 |
|------|---------|
| 客戶端呼叫 RNG 決定捲軸停止位置 | 玩家可修改客戶端操縱結果 |
| 伺服器回傳「種子」由客戶端展開結果 | 結果可預先計算，等同客戶端決定 |
| 伺服器回傳完整結果，但客戶端計算賠付額 | 賠付計算可被操縱 |
| 客戶端先播動畫、事後才向伺服器確認 | 結果與記錄可能不一致 |

**正確流程**見 `rng-game-logic.md` §4 六階段生命週期。關鍵是**投注扣款、結果決定、賠付計算、日誌寫入必須在伺服器端完成且為原子操作**，客戶端收到的是既成事實。

⚠️ 這是顧問應主動檢查的紅旗項目。發現客戶端決定結果時，應中斷其他討論優先處理——這需要重寫核心邏輯，不是補文件能解決。

## 3. 斷線與未完成局處理

玩家在旋轉中斷線是必然事件，處理方式是認證審查重點。

### 3.1 核心原則

**結果一旦由伺服器決定並記錄，即為最終結果，不因斷線改變。** 玩家重新連線後必須看到該結果並取得應得賠付。

錯誤做法：斷線時取消該局並退還投注。這會產生可被利用的漏洞——玩家可在看到不利結果時主動斷線。

### 3.2 未完成局（Incomplete Game）狀態機

需要處理的狀態：

| 狀態 | 定義 | 復原行為 |
|------|------|---------|
| 投注已扣款、結果未決定 | 伺服器在決定結果前失效 | 依市場規則：完成該局或退還投注並記錄 |
| 結果已決定、未回傳客戶端 | 最常見的斷線點 | 重連後回放結果並完成賠付 |
| 多階段功能進行中（free spin、bonus round） | 玩家在功能中途離線 | **必須保存進度**，重連後從中斷點繼續 |
| 賠付已計算、未入帳 | 錢包交易失敗 | 需具備補償交易與對帳機制 |

**多階段功能的狀態保存**是實作量最大的一項。free spin 剩餘次數、累積 multiplier、已收集的符號都必須持久化，且必須能跨會話、跨伺服器實例復原。若使用記憶體內狀態，伺服器重啟即遺失玩家權益，這在認證時會被判定為缺陷。

### 3.3 錢包交易的幂等性

投注扣款與獎金入帳必須具備**幂等性（idempotency）**：同一筆交易重送不得重複扣款或重複入帳。

實作要求：每筆交易帶唯一交易識別碼，錢包端以該識別碼去重。網路重試在分散式系統中不可避免，缺乏幂等性會導致餘額錯誤，而餘額錯誤在博彩系統中是嚴重合規事件。

## 4. Game Recall（遊戲回溯）

多數市場要求系統能回溯顯示玩家近期的遊戲記錄，供玩家查詢與爭議處理。

### 4.1 一般要求

- 能顯示最近 N 局的完整資訊（局數要求依市場而異，需個案確認）
- 每局須包含：時間戳、投注額、捲軸結果、命中的賠付組合、賠付額、餘額變化
- 多階段功能須能顯示完整過程，而非僅最終結果
- 玩家可自行查詢，不需客服介入

### 4.2 與稽核日誌的關係

Game recall 是**面向玩家**的功能；稽核日誌是**面向監管機關**的記錄。兩者資料來源應相同（單一事實來源），但呈現與保存要求不同：

| 面向 | Game Recall | 稽核日誌 |
|------|------------|---------|
| 使用者 | 玩家 | 監管機關、實驗室、內部稽核 |
| 保存期 | 較短（近期若干局） | 長期（見 §7） |
| 不可篡改性 | 建議 | **強制** |
| 內容深度 | 玩家可理解的層級 | 含 RNG 原始值等技術細節 |

不要用同一份資料同時滿足兩者的保存策略——稽核日誌的長期不可篡改保存成本高，而 game recall 只需近期資料。

## 5. 軟體完整性驗證

### 5.1 雜湊值與版本綁定

實驗室認證的是**特定建置**，不是「這個遊戲」。因此：

- 每個送測建置須有可驗證的雜湊值
- GLI-11 要求以雜湊進行程式識別時，訊息摘要輸出**至少 128 位元**
- 上線建置的雜湊值必須與認證建置一致
- 建置雜湊值須與 PAR sheet 綁定（見 `math-verification.md` §3.1）

### 5.2 上線後的完整性檢查

西維吉尼亞 179 CSR 10 §10.8 要求軟體認證嘗試的結果須保存於電子日誌。這代表系統需要：

- 定期或啟動時驗證執行中軟體的完整性
- 記錄每次驗證的結果（含失敗）
- 驗證失敗時的處理程序（停止服務並通報，而非繼續運行）

## 6. 監管機關中央系統整合

這是平台層最容易被低估的工作量。多個市場要求與監管機關營運的中央系統即時整合，這些是**硬性外部依賴**——系統不可用即無法合法營運。

| 市場 | 系統 | 用途 | 信心 |
|------|------|------|------|
| 德國 | **LUGAS** | 跨營運商並行遊戲控管、啟動檔案；切換營運商需 5 分鐘等待期 | HIGH |
| 德國 | **Limitdatei** | 跨營運商月入金限額（§6c） | HIGH |
| 德國 | **OASIS** | 全國封鎖／自我排除檔案（§8） | HIGH |
| 英國 | **GAMSTOP** | 全國自我排除 | MEDIUM |
| 瑞典 | **Spelpaus** | 全國自我排除；2026-08-01 起須以主管機關發放的 Actor ID／API key 查詢，含直效行銷前查詢 | HIGH／MEDIUM |
| 丹麥 | **ROFUS** | 全國自我排除，上線前查詢為技術牌照要求 | HIGH |
| 丹麥 | **SAFE + TamperToken** | 賭博資料持續傳輸至主管機關資料倉儲，以 TamperToken 保護完整性 | HIGH |
| 荷蘭 | **CRUKS** | 全國自我排除，授予存取前強制查詢 | HIGH |
| 義大利 | ADM 遠端遊戲自我排除 | 中央自我排除 | HIGH（存在）／MEDIUM（機制） |
| 西班牙 | **RGIAJ** | 賭博禁入總登記簿，強制查詢 | MEDIUM |
| 安大略 | iGO 集中自我排除方案 | 單一登記涵蓋全省受監管網站；iGO 須於登記後 1 小時內加入登記簿；營運商須於 24 小時內停止行銷並取消退還未結投注 | HIGH |
| 紐澤西 | 自我排除方案 | 可分別選擇實體／線上／兩者 | HIGH |
| 密西根 | 線上博彩與運動賭博負責任博彩資料庫；另有 Disassociated Persons List（實體） | 雙軌 | HIGH |
| 賓州 | 分別的 Casino／iGaming／VGT／Fantasy 自我排除名單 | 多軌 | HIGH |
| 康乃迪克、德拉瓦、西維吉尼亞 | 州級自我排除方案 | — | HIGH |

### 6.1 整合設計要求

**Fail-closed**：中央系統不可用時，正確行為是**拒絕**開始新遊戲，而非放行。fail-open 會導致已自我排除玩家能夠遊玩，這是嚴重違規。

**查詢時點**：不同市場要求不同時點（帳戶建立、登入、每次投注前、行銷發送前）。瑞典 2026-08 起明確要求**直效行銷前**也須查詢。設計時應把查詢設為可插入多個檢查點的服務，而非只在登入時呼叫一次。

**快取風險**：為效能而快取自我排除狀態有合規風險——玩家可能在會話中途登記自我排除。安大略要求 iGO 於 1 小時內加入登記簿、營運商 24 小時內停止行銷，這暗示了可接受的傳播延遲，但顧問應個案確認而非假設。

**多軌名單**：賓州有四個獨立名單、密西根有兩個。整合時不能假設「一個市場一個名單」。

## 7. 稽核日誌與資料保存

### 7.1 已確認的保存期

見 `jurisdiction-matrix.md` §4.2。摘要：瑞典 5 年（遊戲系統運作全部資料）、西維吉尼亞 5 年（玩家遊戲與帳戶活動）＋生命週期後 7 年（開發文件）、密西根 5 年、安大略 3 年最低。英國、德國、丹麥、馬爾他未確認。

### 7.2 保存與刪除的衝突

⚠️ 德國 §6h(5) **要求並行遊戲資料在等待期後刪除**並禁止其他用途。這與「一律長期保存」的直覺相反。

因此稽核日誌不能採單一保存策略，必須按資料類別分別定義：

| 資料類別 | 策略 |
|---------|------|
| 遊戲局結果與賠付 | 長期不可篡改保存 |
| 玩家帳戶與交易 | 依市場保存期 |
| 身分與位置驗證記錄 | 依市場保存期（西維吉尼亞明列於 5 年範圍內） |
| 並行遊戲控管資料（德國） | **到期強制刪除** |
| 個人資料 | 依 GDPR 最小化與目的限制（見 `data-protection-privacy.md`） |

### 7.3 不可篡改性實作

要求：日誌一旦寫入不得修改或刪除（保存期內）。可接受的實作包括 append-only 儲存、WORM 儲存、雜湊鍊、或寫入後即時複製至獨立不可寫入的儲存。

**監管機關存取**：多個市場要求監管機關能直接存取。丹麥透過 SAFE 資料倉儲＋TamperToken；其他市場可能要求提供查詢介面或定期報送。這是架構要求，須在設計階段確認。

### 7.4 時間戳與時鐘

康乃迪克技術標準 §2.1.38 要求平台使用系統時鐘進行所有時間戳，並提供匯出（CSV、XLS）供分析與稽核。

實務要求：所有系統元件的時鐘須同步（NTP），時間戳應含時區或統一使用 UTC。跨時區營運時，**監管機關要求的報表通常以當地時間為基準**，但儲存應以 UTC，呈現層轉換。混用會導致對帳差異。

## 8. 資料落地與部署架構

### 8.1 已確認的硬性要求

| 市場 | 要求 | 信心 |
|------|------|------|
| 瑞典 | 遊戲系統須位於瑞典境內（除有監理協議或滿意的遠端存取控制） | HIGH |
| 西維吉尼亞 | 資料倉儲須為位於該州內的伺服器；另對每台伺服器有 DNS 解析要求 | HIGH |
| 紐澤西 | 互動博彩運算設備須位於大西洋城／紐澤西州內 | MEDIUM |
| 康乃迪克 | 真人娛樂場遊戲須於州內安全遊戲環境進行 | MEDIUM |
| 比利時 | 伺服器須位於比利時並連結實體牌照 | UNVERIFIED |

### 8.2 對架構的影響

資料落地要求會決定部署拓撲，且**發現得越晚成本越高**：

- 單一全球部署 + CDN → 在瑞典、西維吉尼亞不可行
- 區域部署（EU、US、APAC）→ 可滿足部分市場，但瑞典與美國各州的州級要求仍需個別處理
- 逐市場部署 → 滿足所有要求但營運成本最高

**顧問應在市場進入評估的第一階段確認資料落地**，而非留到認證準備階段。這是 `advisory-engagement.md` §1 階段一的必問項目之一。

### 8.3 地理定位（Geolocation）

美國各州與部分市場要求驗證玩家實體位置：

- 西維吉尼亞：僅接受經驗證實體位於該州的玩家投注（HIGH）
- 德拉瓦：軟體須能驗證玩家實體位於州內（MEDIUM）
- 一般模式：州界附近需高精度定位，且須防範 VPN／代理

位置驗證記錄須保存（西維吉尼亞明列於 5 年保存範圍）。

## 9. 獎池系統（Jackpot Controller）

適用於有累積獎金的產品。另見 GLI-12 Progressive Jackpots v3.0。

### 9.1 要求要點

- 貢獻率、種子值、命中機率須文件化並與 PAR sheet 一致（見 `math-verification.md` §3.1 第 13 節）
- 貢獻累積須可稽核，能對帳到每一筆投注
- 命中處理須為原子操作，避免重複派獎
- 跨遊戲或跨營運商共享獎池時，需確認各市場是否允許
- 獎池資金的隔離與償付能力可能有監管要求（屬營運商責任）

### 9.2 德國的特殊情況

⚠️ **德國明文禁止 jackpot**（§22a(8) 第二句 Jackpotverbot），且要求獎金必須是遊戲開始前即確定的投注倍數（第一句）。

這代表德國版本不能只是「關閉獎池控制器」——必須是移除累積獎金機制、且 RTP 重新分配後的獨立數學模型（見 `jurisdiction-matrix.md` §1.5）。

## 10. 平台層送測前檢查清單

- [ ] 送測範圍已確認含 RGS、錢包、PAM、獎池控制器、日誌子系統，非僅遊戲
- [ ] 遊戲結果完全由伺服器決定，客戶端無法推導或影響
- [ ] 投注扣款、結果決定、賠付計算、日誌寫入為原子操作
- [ ] 斷線復原：已決定的結果不因斷線改變
- [ ] 多階段功能（free spin、bonus）進度已持久化，可跨會話與跨實例復原
- [ ] 錢包交易具備幂等性，重送不重複扣款或入帳
- [ ] Game recall 可顯示所需局數的完整資訊，含多階段過程
- [ ] 建置雜湊值（≥128 位元摘要）已記錄並與 PAR sheet 綁定
- [ ] 上線後完整性驗證機制存在，失敗時停止服務並記錄
- [ ] 目標市場的中央系統整合已完成（自我排除、限額、並行控管）
- [ ] 中央系統整合為 fail-closed，不可用時拒絕新遊戲
- [ ] 自我排除查詢已插入所有必要檢查點（含行銷發送前，瑞典要求）
- [ ] 多軌自我排除名單已處理（賓州四軌、密西根雙軌）
- [ ] 稽核日誌不可篡改，保存期符合目標市場要求
- [ ] 資料保存與刪除按類別分別定義（含德國 §6h(5) 強制刪除）
- [ ] 監管機關存取機制已建立（丹麥 SAFE／TamperToken 等）
- [ ] 所有元件時鐘同步，時間戳統一基準
- [ ] 資料落地要求已確認並反映於部署拓撲
- [ ] 地理定位機制與記錄保存已就緒（適用市場）
- [ ] 介面合規責任矩陣已與營運商逐項確認，無檢查點落空
